Proposed Sidequestor dashboard theming scope

Goal: preserve the current dashboard as the built-in default. Users override styling with files in <workspace>/theme/. Emptying or deleting that folder restores the default after refresh. Implemented as 0.2.8.dev0; see implementation status below.

1. Load theme/custom.css after ALL bundled dashboard styles using a same-origin stylesheet link. Missing or empty file returns an empty CSS response. Read fresh on each request and use no-store, so edits/reset require only refresh, no restart. Never create or regenerate custom.css or theme/ automatically. Scope is per workspace.
2. Expose /theme/ through narrow read-only routes for CSS, local raster images and fonts. Resolve paths inside the workspace theme directory, reject traversal and symlink escapes; no directory listings, arbitrary workspace files, scripts or HTML. Retain existing dashboard authentication, Host checks and response security headers. Initially exclude SVG and other active document formats to keep asset serving small. Keep current CSP restrictions on network origins. Document local asset relative URLs.
3. Preserve built-in CSS appearance. Expand existing root variables only where necessary for coherent customization (backgrounds, semantic status colors, fonts, key radii/spacing/shadows). Document stable tokens and existing CSS selectors as best-effort examples; defer a new component-hook API. retain existing token names as aliases if semantic names are introduced. Arbitrary CSS overrides supported best effort; do not promise DOM/layout compatibility. Avoid broad CSS rewrite.
4. Bundle a concise yaas-dashboard-theme skill through the existing skill packaging/discovery mechanism. This is an additive documentation skill, not an engine behavior change. It helps agents find the workspace, preserve existing customizations, edit only theme files, use supported tokens, preview real screens where tools permit, check contrast/mobile/focus states, and explain reset. It must not edit packaged HTML, engine code, task state, approval controls, worker settings, or install scripts for customization. No bespoke installer changes: existing resource sync automatically discovers yaas-* skills.
5. Document theme/custom.css with a minimal example, token contract, local assets, refresh/reset, upgrade ownership and limitations. No manifest required for one active theme; record theme API v1 in documentation for future compatibility.
6. Verify observable default rendering and overrides; deletion/empty-file reset; fresh edits; workspace isolation; traversal and symlink blocking; proper content types/auth/security headers; existing dashboard behavior and bundled skill discovery. Upgrade preservation checked through existing resource sync in temporary workspace. No publication or upgrade of live workspace.

Allowed changes: dashboard HTML/CSS and its HTTP presentation/asset-serving code, new bundled skill docs, user docs and focused tests. Out of scope: triage, dispatch, scheduling, checkers, quests, approvals, action execution, connectors, engine configuration, resource-sync logic, migrations, animation/event plugins, visual editor, theme marketplace, uploading/remote assets and custom JS/HTML. Dashboard server is physically stored under runtime/yaas-triage/ops; touching its presentation routes is necessary, but no engine semantics or existing API contracts should change. Skill is stored under runtime skills and uses existing sync unchanged.

Claude review completed successfully on 2026-10-31. Authentication required running the CLI outside the sandbox; the review had tools disabled and received only this plan. Claude judged the scope sound and appropriately small. The following refinements are accepted; this remains a proposal with no implementation changes.

Final v1 refinements:
- Freeze the token list before implementation: retain existing ink/muted/faint/paper/surface/line, blue/blue2, teal/teal2, amber/amber2, red/red2, shadow, mono and sans tokens. Add only page background, control background, focus-ring color, base font size and card radius for the initial documented example. Defer comprehensive spacing and component-token conversion. Record exact defaults before changing CSS so the default appearance remains equivalent.
- Place the custom stylesheet link last in head, after every bundled style block. CSS overrides do not universally beat inline style attributes or existing !important declarations; document the cascade rather than promise unrestricted replacement.
- Missing, empty, unreadable or oversized custom.css returns 200 text/css with an empty body. Set a documented 1 MiB CSS limit and 10 MiB per other asset; oversize other assets return 413. Bound reads rather than loading unbounded files. CSS and assets use Cache-Control: no-store.
- Use a fixed extension-to-MIME allowlist for CSS, PNG/JPEG/GIF/WebP/AVIF and WOFF/WOFF2; nosniff and existing security headers. Exclude HTML, JavaScript, SVG, dotfiles and directory listings. Theme routes are read-only. Validate decoded paths, reject traversal/backslashes/nulls, and check resolved containment by path components. Reject symlinked theme roots outside the workspace and asset symlinks escaping the resolved theme root. Keep one resolved root per request. No generic static-files server.
- Preserve Host validation, authentication ordering and status codes (the current dashboard uses 403, not Claude's suggested 401). Allow same-origin fonts explicitly in the HTML CSP if needed; keep remote origins blocked. Asset responses must not create state or acquire engine locks.
- All upgrades/resource sync leave theme files byte-identical and never create, repopulate or remove theme/. Test both populated and empty directories. Reset means deleting the folder and refreshing; stale theme assets must not survive via HTTP caching.
- If semantic aliases are added later, new tokens supply defaults and legacy names reference them. Both override paths must work. Defer unnecessary renaming in v1.
- The bundled skill points to one maintained detailed theming reference, rather than duplicating the token contract. It edits user theme files only and explains filesystem reset prominently.
- Verification covers actual rendering of defaults, override/cascade, edits/reset, asset paths/auth/CSP, resource-sync preservation, existing dashboard interactions and bundled skill discovery. Preserve API behavior and engine-state invariants; do not require volatile response bodies to be byte-identical.

Final boundary: presentation only, plus additive skill documentation and focused tests. The dashboard HTTP server and packaged skills physically live under runtime/yaas-triage; those presentation/doc files are allowed. No engine behavior, resource-sync algorithm, API contracts, task execution or live-workspace changes are authorized by this plan.

Implementation note (2026-10-31): v1 uses descriptor-relative file opens and rejects all theme symlinks, including the theme root. Token defaults, asset limits, last-in-head loading, no-store responses and the bundled skill are implemented in the 0.2.8.dev0 worktree; verification and local installation are tracked in the implementation session.
