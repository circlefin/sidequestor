Problem

The six-status machine is written independently on both sides of the seam, and the two have already diverged.

Solution

One transition table on the server; the route list derives from it; the client's only job becomes switch(item.status).

Deletion test

Concentrates. Deleting the client's re-derivation removes ~60 lines of status branching and leaves the machine in one file with one lock. The optimistic dismissal set stays — it is presentation, not state, and re-renders from server truth on the next poll.

Three features that shipped broken — all verified against the running code
  1. Undo and in-flight save never work. The client fetches /api/undo/<id> and /api/edit/<id>; do_POST routes only review|revise|cancel|prompt. Both 404.
  2. The stalled/reclaim UI is unreachable. dashboard.html:841 gates it on item.stalled. No Python emits that field for an approval item — the only "stalled" in the tree is in run-agent.py, for an unrelated worker-stream concept.
  3. In-flight items render twice. build_messages puts every non-terminal item in needs_you/other_actions and every reviewed/executing item in queued_items — so it appears in the strip and as a carousel card whose buttons the server 409s. The client comment at :837-840 asserts the opposite.

Root cause is architectural, not careless: commit 309aab8 is 141 insertions across one file — dashboard.html, zero server lines. When the machine lives on both sides, a client-only commit compiles, renders, and silently half-works.

Wins
  • One state machine, one file
  • Undo and edit endpoints exist
  • In-flight items stop rendering twice
  • Reclaim UI gets a producer
  • locality: transition bugs land server-side

Already deep — leave alone

Proposing damage is the failure mode of this exercise.

tick_state.load_lag_map + runtime checker resolution

~9 lines: one glob, one path join — and the 1,496-line orchestrator never learns the type set. This is the pattern the rest of the repo should copy; candidate 2 is an extension of it, not a replacement.

The executable bit as type/helper discriminator

result.py and slack_utils.py are non-executable, and checker-contract.test.sh:161-168 asserts they stay that way — so a helper can never be dispatched as a checker. A cheap filesystem fact carrying a real invariant, with a test pinning it.

reaction_config.py (65 lines)

Not a constant holder — the constants are 8 of 65 lines and the validation is the point. One zero-argument interface hiding env resolution over 6 roles, :emoji: stripping, shape validation and a cross-role uniqueness check. 5 consumers in a repo with ~21 import edges.

dispatch/slack-read-health.py (159 lines)

Interface is a boolean. Implementation hides three unrelated agent stream formats plus recursive error-envelope detection through JSON-in-strings. Only 1 call site, so leverage is low — but depth is high and every "did Slack actually read?" bug lands in one file.

Top recommendation

Give the approval state machine one definition → candidate 1

It is the only candidate that is already costing you working software. Three features in the newest commit — Undo, in-flight save, and stalled-item reclaim — are shipped and dead, and a fourth renders every in-flight item twice with buttons the server rejects. None of that is carelessness: the machine is defined on both sides of the seam, so a client-only commit of 141 lines compiles, renders, and silently half-works. Fix the seam and the four defects stop being possible rather than being fixed one at a time.

Then candidate 2 — the watch-type manifest — because it is the highest-leverage structural change here and the repo has already proved the pattern works with .lag. Candidates 5 and 6 fall out of candidate 1 almost for free.
